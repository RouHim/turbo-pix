## Code Style

**Backend / Rust:**

- Iterator chains over loops: `.iter().filter_map().next()`
- Arrays over vecs: `[A, B]` vs `vec![A, B]`
- Error handling: `Result<T, E>` with `?`
- Imports: std, external crates, local (blank lines between)
- Zero warnings policy

**Frontend / Svelte 5 (runes) + Vite:**

- `const` over `let` (no reassignment)
- Arrow functions: `() => {}` over `function() {}`
- Template literals: `` `string ${var}` `` over `'string ' + var`
- When adding visible text to the frontend, add them to the `i18n` translation system.
- When changing frontend files: run `npm run build` first, then `cargo build --bin turbo-pix` (build.rs embeds dist/ and panics if it is missing)

**General:**

- KISS: Keep It Simple, Stupid (DRY, YAGNI, etc.)
- SOLID principles (single responsibility, open/closed, etc.)
- Zero linting issues - investigate each issue in detail, don't just silence it

## Learnings

**Capped at 10 entries (decision 2026-08-11).** These are the top-10 most relevant project traps. When a session produces new learnings, fold them into an existing entry or replace the least relevant one — never append standalone entries.

1. **i18n parity & integrity guard:** keys are dot-paths into nested JSON dictionaries; `en.json` and `de.json` MUST stay structurally identical — every new key lands in BOTH. `tests/i18n-integrity.test.js` (`npm run test:i18n`, wired into the CI lint-format job) scans every `$t`/`get(t)` literal, template, and map key (Sidebar/SortControls `key:` fields, App's `titleKeys`) in `frontend/src` and fails listing ALL missing keys plus parity drift; template `${…}` placeholders must be one of its `enums` map entries. `$t` options: pass `values` INSIDE the options object for keys containing `{...}` (a third argument is silently dropped); the positional fallback `get(t)(key, 'fallback')` does not work — use `{ default: '…' }`. The playback notices this rule bit last are `video.stream.buffering` / `video.stream.waiting` (the waiting one is shown for a saturated conversion pool). The other node tests run behind `npm run test:unit` (`node --test tests/*.test.js`, in the same CI lint-format job alongside `test:i18n`): `tests/mse-player.test.js`, `tests/encoder-hint.test.js`, `tests/timeline-model.test.js`, `tests/timeline-layout.test.js`, `tests/timeline-route.test.js` and `tests/map-aggregates.test.js` (the old `timeline-aggregates.test.js` went with the year aggregates) — a new `tests/*.test.js` file is picked up automatically; `tests/**` is prettier-checked but never eslint-linted (only `frontend/src` + configs are), so a slip there surfaces at runtime, not in lint.

2. **State & routing:** the `route` store (`router.svelte.js`) and `$state` stores (`state.svelte.js`) are the single source of truth — components render from them, never mirror values into write-only fields; `$state` fields MUST use `let` (const trips eslint's `no-const-assign`). The timeline filter lives in the URL as `year`/`month` (start bound) plus `to_year`/`to_month` (end bound; absent = a single period, absent `month` = the whole year). Route-restore trap: TimelineSlider's sync effect must read `route.year`/`route.month` BEFORE the `dragInProgress` guard — reading a debounced-writer field first wipes the in-progress filter on every drag tick, and an early return that reads nothing replaces the effect's dependency set with `{}`, permanently unsubscribing it (Back/Forward never restores). A restored selection that no longer overlaps the library is rewritten to the canonical clamped filter by `TimelineSlider`'s replaceState `$effect`, which reads `data`/`filter`/`filterFromSelection` BEFORE its loaded guard (an in-flight fetch must never be read as "the data is gone"); live scrubbing `replaceState`s at most every 100 ms while the overlay follows the pointer immediately. In `TimelineSelector`, view `$effect`s MUST assign `view` only when `scale`/`origin` actually changed (`clampView` returns a fresh object, so an unconditional assign self-retriggers), MUST read `width`/`model` inside `untrack` for the `resetNonce` reset (otherwise every resize throws the zoom away), and MUST skip while the lane width is 0 (the mobile `display: none` breakpoint). FR-007 — a period with no photos is never selectable: activating a zero-count column returns early and a selection that is exactly one zero-photo month is refused on every commit path (a wider range merely containing empty months stays legal); handles and the overlay paint clamped into the lane because a bare `?year=` deep link may start left of the first populated month.    The selector's granularity IS the rendered column unit (`chooseUnit(view.scale)`,
   `frontend/src/lib/timelineLayout.js`): the Decade/Year/Month pills are view-only and press whatever the lane
   renders (`aria-pressed={unit === level.unit}`, an activation while already at that level is a no-op), a click on a
   decade/year/month column commits exactly that period and drills one level in by clamping the period's span into the
   next unit's band (`zoomToUnitRange`, band edges from `unitScaleMin`/`unitScaleMax` with a 1e-3 margin so a clamped
   scale can never land on `chooseUnit`'s `>=` threshold; below the band the unit is kept and the period shows
   partially — never a coarser fallback), and the level pills frame the active filter when it fits the level's window
   and otherwise a window around the current view centre (`frameUnit`) without ever writing a filter. Both framings set
   `reframeSuppressed` before writing `view`, or the FR-010 selection-following effect reverts them. A grid-aligned
   decade filter (`?year=1960&to_year=1969`) is a *period*: `selectionFromFilter` keeps its own January–December-ten-year
   bounds (`isDecadeFilter`), so the header reads `1960s` instead of the clamped `March 1962 – December 1969` and the
   round trip stays the identity; a non-decade or shifted ten-year range keeps clamping as before. A commit whose
   canonical filter already equals the route filter is skipped, so re-activation adds no history entry. Decade labels go
   through `ui.timeline_decade_label` (`{start}s` / `{start}er`) — never hardcode the `s` — and the year dropdown gains
   an option for a filtered year the library has no bucket in, or it silently reads "All Years" over a filtered grid.
   Node-testable modules MUST NOT import `utils.js` — it imports `../i18n/en.json` without the JSON import attribute, so `node --test` dies at link time with `TypeError: Module "…/frontend/src/i18n/en.json" needs an import attribute of "type: json"`; keep shared pure helpers in their own module (`lib/query.js` `isPrefixQuery`, `lib/map.js`) and inject the api client instead of importing it. Geo-coordinate validation lives solely in `frontend/src/lib/map.js`'s `getPhotoCoordinates` on the frontend — non-numeric, single-coordinate, and out-of-range values are dropped there before clustering (the backend is the other gate: `src/metadata_writer.rs` rejects out-of-range and unpaired coordinates, which `PATCH /api/photos/{hash}/metadata` maps to a 400). GPS and the capture date are FILE facts, never stored ones: `taken_at` is a response-only field (`FromRow` yields `None`, only `MediaFactsIndex::enrich` fills it) and coordinates come from the file's EXIF through the same index (entry 9), while the DB keeps just the resolved place name at `$.location.city` (`json_extract`; no dedicated columns) — `db::stored_metadata` strips `latitude`/`longitude` from EVERY write, so a stored coordinate pair can only be pre-migration residue. `PATCH /api/photos/{hash}/metadata` writes ONLY the file's EXIF (dates/GPS) plus the row's `updated_at`, so an already-resolved `city` survives a coordinate edit and a test that needs a nameless location must still pick a photo that has none. Only the writer's range/pair errors reach the client as a 400; every other writer refusal is the sanitized 500 (`handle_rejection` logs the real message, the body is just "Database error") — and the writer refuses every extension but JPEG/PNG, which is why the viewer DISABLES the metadata-edit control for a video/RAW/WebP instead of letting the user hit that 500 (so a video can never carry map coordinates).

3. **Scoped styles beat global overrides:** global `@media`/`@container` rules and `@layer utilities` helpers of equal-or-lower specificity are outranked by scoped `svelte-*` selectors — responsive overrides MUST live in the component's scoped `<style>`, never in `app.css` where they silently no-op. Dead-CSS deletion is property-level: a global rule is only dead where the scoped rule sets the SAME properties. Keep `build.cssMinify: false` in `vite.config.js` (Lightning CSS collapses `backdrop-filter` pairs to the `-webkit-` form Chromium ignores). The timeline selector's geometry (ruler/lane heights, the 24px handle hit zone) likewise lives in `TimelineSelector.svelte`'s scoped `<style>`; its label collision avoidance measures `getComputedStyle(probeEl).font`, so the hidden `.timeline-label-probe` span must stay in the DOM. A native `<video>`'s control strip is painted INSIDE the element's own bottom edge, so a height-bound video (any portrait clip, or a 16:9 source in a 16:9 viewport) drops the scrubber onto the floating viewer action bar: the scoped `.viewer-controls` rule in `frontend/src/components/ViewerControls.svelte` and the `.viewer-main.video-mode` reserve in the sibling `PhotoViewer.svelte` both read `--viewer-controls-offset`/`--viewer-controls-height`, with the mobile offset override in an `app.css` `:root` media query so the media box sees the same value. Like `<video>` default boxing, video E2E geometry assertions MUST first wait for `videoWidth > 0` — before metadata resolves the element lays out at Chromium's 300×150 default and overlap assertions pass vacuously. Stylelint blindspot: `lint:css` only globs `frontend/src/**/*.css`, so invalid CSS pasted into a Svelte `<style>` block (e.g. stray diff `+` markers) passes lint and breaks only at `vite build` — always run `npm run build` after style edits.

4. **Viewer async staleness:** every async continuation in `PhotoViewer.svelte` must re-check `currentPhoto?.hash_sha256 === photo.hash_sha256` before acting (`displayVideo` after the server `video?decision` fetch AND after the transcode-spawn `fetch`, `pollTranscodeStatus` at interval top AND after every `await`, `onerror` handlers); continuations touching the URL/navigating must also bail when `!isOpen`. `pollTranscodeStatus` shares a module-level timer — capture the id in a local `const`, only clear/null the shared field when it still points at YOUR interval. Guard `startViewTransition` callbacks with `if (!isOpen) return;` (the callback runs on the next frame).

5. **Silent-failure registries (icons, tiles):** feather only, no emojis. An unregistered `<Icon name>` (including dynamic bindings) renders an EMPTY string silently — no build error, no console warning; every icon MUST be registered in `frontend/src/components/Icon.svelte`; grep `name="`/`name={` usages against the registry. The runtime regex strips the raw `class="feather …"`, so `:global(.feather)` never matches — size icons via `:global(svg)`. Same class of trap in the Map view: the Leaflet tile URL comes from `GET /api/config` (`TURBO_PIX_TILE_URL` → `appState.tileUrl`) and must never be hardcoded, and attribution is registered on `map.attributionControl` — NOT on the tile layer — so it stays visible when every tile request fails.

6. **Rotation & photo identity:** `image::save` re-encodes from pixels and drops EXIF — read EXIF from the ORIGINAL before the transform and write it into the temp file with Orientation forced to 1 (skip `Value::Unknown` and `In::THUMBNAIL` fields), via `src/exif_helpers.rs` (never hand-roll `exif::Reader::new()`); EXIF writes are atomic sibling-temp + rename. Rewriting `photos.hash_sha256` violates the `housekeeping_candidates` FK (no `ON UPDATE`) — delete the stale candidate row in the SAME transaction; `Photo::update_with_old_hash` takes a `&mut sqlx::Transaction` and checks `SELECT changes()`. `hash_sha256` is a PATH-string hash on purpose (favorites stay stable across in-place edits) — thumbnail/transcode/collage caches fold a size+mtime CONTENT VERSION into their keys, and `clear_for_hash` removes every `{hash}_*` file. Album membership (`album_members`) references `photos(hash_sha256)` AND `albums(id)` with `ON DELETE CASCADE` both ways — library removals and album deletions clean up membership for free, but only because sqlx enables FK enforcement; cascade claims need a dedicated test, never a pragma.

7. **Native-first video serving & codec-agnostic transcode:** playback decisions live SERVER-SIDE — `get_video_file` runs `video_capability::plan()` over the capability record (codec/container/bit-depth/`moov_at_start`) against the client's declared codecs (`X-TurboPix-Codecs` header or the `client` query param, header wins; missing → conservative h264-8; the web app can only use the query param, because a media element's own request cannot carry a request header). An INCOMPLETE legacy record must never select conversion: `video_probe::resolve()` probes the file once, persists the derived facts plus `capability_version` (`CAPABILITY_VERSION`; `record_is_complete` needs it AND either a non-empty `codec` or `no_video_stream: true` — that pair is the "complete, never probe again" marker, a bare version marker stays incomplete) into `photos.metadata.video`, and only then plans — an absent container/`moov_at_start` key means "never probed", not "unplayable"/"true", and no pass may INVENT one: a moov pass that yields no verdict (killed at its deadline, a transient ffprobe failure) keeps the record's stored `moov_at_start` and writes NO layout key when the record has none (the version marker and the derived facts still complete it — the layout just stays unknown), while `plan` treats "unknown" as not-progressive for an MP4-family source (`Some(true)` is the only progressive verdict) and takes the `-c copy` faststart remux rung instead of `Direct`, which for a moov-at-end original means the browser downloads the whole file before the first frame, permanently — the remux is a plain rewrite for a source that was already faststart. Appending `?decision` (bare or `=true`) returns JSON `{action: direct|stream|empty, url, mode, mime, duration, cached, reason}` — always 200, never 202; the 202 + `poll_url` handshake belongs to the transcode SPAWN (`?transcode=true`), not the decision probe, and a cached artifact comes back as `direct` + `cached: true` (a served conversion URL carries `transcode=true`, because a plain byte request would re-decide and could hand back the source codec). Transcode is codec-AGNOSTIC (`convert_video_with_progress`, not hevc-only) and gated by a worker pool: `transcode_semaphore()` is `OnceLock` and locks in the FIRST `transcode_max_pool()` it saw — `TURBO_PIX_MAX_TRANSCODES` (0 = disabled, checked before touching the semaphore; absent → `min(max(nproc/2,1),4)`), timeout via `TURBO_PIX_TRANSCODE_TIMEOUT_SECS` (default 300); no test reset hook, so tests assert `transcode_max_pool()` directly. `/video/stream` streams fragmented MP4 out of a live ffmpeg and takes the SAME permits (`acquire_transcode_permit`): a request that finds the pool full WAITS up to `TURBO_PIX_STREAM_QUEUE_WAIT_SECS` (default 20 s, warn + default on a bad value) and then answers `503` + `Retry-After` (2 s; 5 s when conversions are disabled) — that wait is user-visible, never a silent spinner: the viewer keeps its waiting notice ("waiting for a free conversion slot") up across the retries, re-runs the refused request on the same mode (a refusal says nothing about the mode) and resumes the NEWEST position the user asked for — `streamIntentOffset`, refreshed by every run the player begins (`onRunStart`, including one `msePlayer` restarts for a seek) and by any move the user makes on the element (`onUserSeek`, which also fires for a buffered target that starts no run) — NOT the offset the REFUSED run asked for, because a seek landing while the server holds that run for up to `TURBO_PIX_STREAM_QUEUE_WAIT_SECS` has already superseded it; those same two signals disarm the retry, so it can neither tear down a newer run nor resume an offset the user has left, while every other stream error climbs the bounded ladder `remux → audio → transcode`, resumes the larger of the element's own position and the offset the FAILED run itself began at (`streamRunStartOffset`, set by its own `onRunStart` — the element alone cannot say where a run that never attached was, because `playStream` clears its source for every run and only a run past its first append re-parks it, so a refusal or a zero-byte body would restart playback at 0:00 on a heavier conversion), and ends at "play the original". The stream's mode is re-planned server-side and a client `?mode=` may only RAISE it (unknown values are ignored, so an old client's query cannot break playback); the mode's MIME arrives per response in `x-turbopix-mime` and MUST type THAT run's SourceBuffer — reusing the decision MIME mis-types an escalated rung. ffmpeg rebases fragmented-output timestamps to 0, so seek mapping lives in the client's `SourceBuffer.timestampOffset` (assigned per run), never in ffmpeg timestamp flags; MSE is also the only seekable path available here — WebCodecs needs a secure context and TurboPix serves plain HTTP on the LAN. MSE details that bite: an append's own `updateend` can be preceded by an update the element starts while the app's `updating` check is already stale (serialize appends and offset assignments on `updateend`), a seek inside the buffered range MUST NOT restart the stream (`start=` only for genuine restarts, and the position the player set itself is not user intent), and one bad delivery raises `error` on BOTH the SourceBuffer and the element — a run-scoped `failureReported` flag (plus an `AbortSignal` check, so a superseded run's late error is ignored) makes that pair cost exactly one ladder step. The run is UNPACED (`ReaderStream::new(stdout)`, no `-re`), so the client owes the back-pressure: the pump stops reading the body once the media buffered ahead of the playhead passes `LOOK_AHEAD_SECONDS` and resumes on the element's next `timeupdate`, and it trims played-out media from that same listener once the pump has ended — so a viewer paused past `TURBO_PIX_TRANSCODE_TIMEOUT_SECS` (300 s) gets its run killed by the stall watchdog, and the body that then ends short of the declared duration MUST surface as the truncation failure (a parked pump that only watches the playhead swallows the body's end and wedges the player) for the ladder to take over. The whole-file caches are three namespaces under `TRANSCODE_CACHE_DIR` — `transcoded/` (universal H.264+AAC re-encode), `copied/` (source video copied bit-for-bit, audio converted) and `remux/` (faststart sidecar, `video_processor::remux_sidecar_path` — `handlers_video` only imports it) — and they are NOT interchangeable: `copied/` keeps the SOURCE codec, so only an audio-mode delivery may be served it, every other delivery plays `transcoded/`, and existence alone means complete — the per-hash conversion status is shared by all three, so it must never gate serving (a failure in one namespace would hide a good artifact in another). `claim_transcode` still consults AND inserts `InProgress` under the status-store lock (the semaphore only serializes, never prevents duplicate spawns); `Failed`/`Timeout` remove leftover `*.mp4.tmp` and serve the original with `X-Transcode-Warning` (`TRANSCODE_RETRY_COOLDOWN` = 15 min). `/video/status` reports `percent` + `deadline_ms`; the Svelte poller stops on the server deadline (+30s grace), never a hard-coded client cap. Status store capped at 128 (`InProgress` never evicted). Crash-debris temps are swept at startup by `sweep_transcode_debris` (any `*.tmp`/`*.moovfix.*` under the cache tree plus `*.moovfix.*` in photo dirs, before the scheduler rescan so debris is never indexed) — but only AFTER the port check, because a second instance that cannot serve must not delete the running instance's in-flight temps (a swept whole-file temp fails its rename and blocks that hash for the retry cooldown; a swept `moovfix` temp aborts a running `fix_moov_atom`) — and cycle-safe by canonical path exactly like `FileScanner::walk_directory`: the sweep runs before `warp::serve`, so a `loop -> .` symlink it follows keeps the server from ever binding (a genuinely symlinked directory must still be swept, and a deep tree still descended; all three behaviours are pinned by tests); per-hash eviction is `clear_transcode_cache_for_hash` on the single-photo delete/rotate paths (`image_editor.rs`, `handlers_photo.rs`) and the batched `clear_transcode_cache_for_hashes` on the orphan scan (`photo_processor.rs`), with `purge_old_transcode_versions` (only `.mp4` versions — a `{hash}_*.tmp` is a conversion IN FLIGHT, e.g. the same hash's remux fill, and is never purged) on every successful conversion, while the file scanner permanently excludes `*.moovfix.*` so crash debris is never indexed as a photo. Every artifact path resolves through `namespace_dir`, because `TRANSCODE_CACHE_DIR` defaults to `{data_path}/cache/transcoded`: the cache ROOT **is** the `transcoded` namespace, so joining another `transcoded` underneath names a directory that never exists — which is how a deleted photo used to keep its re-encode and an in-place edit its superseded version. Every video map is `0:V:0?` (capital `V` excludes the attached cover pictures the resolver skips, the trailing `?` lets a video-less source still convert/stream), and the planless software re-encode pins 8-bit 4:2:0 Main (`-pix_fmt yuv420p -profile:v main`) because the x264 wrapper otherwise keeps the SOURCE bit depth: a 10-bit source came out as H.264 High 10 — the very profile the decision's `h264-10` gate says every client routed there cannot decode — and the cached artifact then failed on every later open. A claim about an encoder is only allowed when the run really encoded video: a `no_video_stream` source and a `copied/` artifact (video passed through) must stay silent on all three carriers, and a video-less source that still carries an audio track must not fail its conversion. Hardware encoder selection is ONE process-wide verdict living in `src/video_encoder.rs`: `init()` runs from `main` before the bind (skipped entirely when `transcode_max_pool() == 0`) and caches `Option<HwPlan>` in the `ACTIVE_PLAN` `OnceLock` behind a `Hardware video encoder: <label>` info line; both transcoding paths take it EXPLICITLY (`build_conversion_args` takes `Option<&HwPlan>`, `start_stream_with_plan` takes it by value as `Option<HwPlan>` — the first-byte gate drops it when it respawns the run in software), which is what keeps the argument builders pure and the CPU path permanently `None`. ffmpeg LISTING an encoder proves nothing about using one: `h264_nvenc`, `h264_qsv` and `h264_amf` are all listed on this host yet cannot open a session, and `/dev/dri/renderD128` (AMD) is listed but has no H.264 encode entrypoint (`No usable encoding entrypoint found for profile VAProfileH264High (7)`) while `renderD129` (Intel) encodes in ~0.09 s — so the probe MUST run the JOB's own argument shape (`-vaapi_device` + `-vf format=nv12,hwupload` + `-c:v h264_vaapi -qp 23`, on the synthetic `color=c=black` input, `-frames:v 3 -f null -`) against every `renderD*` node ascending, first pass wins; a node without an entrypoint must not disqualify the backend. Order is NVENC → VAAPI → QSV → AMF → VideoToolbox — VAAPI outranks QSV because QSV rides the same driver VAAPI drives while needing a libmfx/oneVPL runtime that is frequently absent — and since a broken candidate can hang or burn seconds, every call is bounded by `PROBE_TIMEOUT` (2 s). Parity is by NUMBER, not by bitrate: `-qp 23` / `-cq 23 -b:v 0 -tune hq` / `-global_quality 23` / `-rc cqp -qp_i 23 -qp_p 23` / `-q:v 55` land next to the software `-crf 23` (measured here on 5 s of a 1080p30 HEVC source: libx264 `-preset fast -crf 23` = 2.2 s / 3.13 MB / SSIM 0.9583 vs VAAPI `-qp 23` = 0.75 s / 4.47 MB / SSIM 0.9580 — ~3× faster at equal SSIM for ~40 % larger files, and `-b:v 0` is mandatory because NVENC otherwise clamps to its 2 Mbps default). A hardware failure never costs the user their video: the whole-file path retries ONCE in software inside the SAME job (`convert_with_fallback` warns `Hardware encoder … failed (…); retrying with libx264`, and the finished status then reports `encoder: libx264`), the stream path respawns in software inside the same request but ONLY before its first byte (`take_first_bytes`, `FIRST_BYTES_TIMEOUT` 10 s — a silent-but-alive run belongs to the stall watchdog), and a timeout is NEVER retried because its budget is already spent; both attempts share one `ProgressHighWater`, so the retry's parser restarting at zero cannot drag the client's percentage backwards. The player hint reads that one fact through three carriers — `x-turbopix-encoder` on a live stream run, `TranscodeStatus.encoder` on a finished conversion, and `encoder` in the `?decision` payload for a cached artifact — and SILENCE is the fourth answer: a `FileConversion::VideoCopy` encodes no video at all (`ConversionOutcome.encoder` is an `Option`), which is why the viewer treats an absent header, an evicted status and a copy identically (no hint) and an unknown name as not-hardware (`cpu` icon) — the hint may never claim a GPU it cannot name, and per-playback resets plus the `onEncoder` staleness guard keep it from outliving the run it describes. The decision is a HINT, never an order: the `?decision` payload also carries the source's `codec`/`bit_depth`/`audio_codec`, the viewer attempts the ORIGINAL first (`startOriginalAttempt`: a decoded frame settles it playable, an element `error` refutes it, a reported stall that goes 5 s without a frame times it out, the deadline re-armed while the delivery is being served) and only a demonstrated failure hands over to the named rung — a codec an actual playback proved persists in `localStorage` under `turbopix_verified_video_codecs` (folded into the `?client=` declaration) and per-hash failures are remembered for the session so a reopen skips the window. A `Direct` plan has no rung of its own: the byte endpoint IGNORES `transcode=true` for a directly playable source and serves the ORIGINAL, so a failed direct-plan attempt converts only through `/video/stream` — the endpoint that re-plans, and whose `escalated()` answers a `Direct` plan with the full `transcode` — while asking the byte endpoint hands the viewer the very bytes the attempt just refuted. The audio gate cannot ride on that frame: an unsupported audio track (AC-3/DTS in MP4) is ignored silently — the video frames decode, `playing` fires, no `error`, no `play()` rejection — so "a first decoded video frame" is not a playable-in-full verdict; `canPlayAudioCodec` gates the source's audio token separately, and the escape hatch deliberately opens that gate. A source must be cleared with `removeAttribute('src') + load()`: `src = ''` + `load()` + the real `src` in one synchronous block fires NO `error` on a playable file (measured twice), while an empty-string `src` left in place resolves as a URL and Chromium answers it with `MEDIA_ERR_SRC_NOT_SUPPORTED` — the event msePlayer reads as an undecodable delivery.

8. **Migrations are content-checksummed:** `sqlx::migrate!` records a SHA-384 of each migration file and verifies it on every startup — NEVER edit an applied migration (bricks DBs with `VersionMismatch`); schema cleanups on shipped migrations belong in a NEW migration. Repairing an applied DB: `sqlite3 <db> "UPDATE _sqlx_migrations SET checksum = X'<sha384 of CURRENT file>' WHERE version = ..."`.

9. **SQLite query & bulk-write traps; the file-only date/coordinate invariant:** `delete_orphaned_photos` inserts scanned paths into a per-connection `TEMP TABLE scanned_paths` (multi-row chunks of 500) then runs `NOT IN (SELECT path FROM scanned_paths)` — one placeholder per file exceeds `SQLITE_MAX_VARIABLE_NUMBER` (32766) and silently killed nightly cleanup. All statements on ONE held `pool.acquire()` connection; `DROP TABLE IF EXISTS` before CREATE. Partial scans (`scan_complete = false` when a root is missing / directory unreadable) skip orphan cleanup entirely — deleting rows for temporarily unreachable files would permanently lose favorites/manual metadata. Membership `IN (...)` lists chunk at the same 500; `INSERT OR IGNORE INTO album_members … SELECT … FROM photos WHERE hash IN (…)` makes add/create-from-selection robust to photos that left the library between selection and submit (unknown hashes silently skip). `build_search_where` (`src/db.rs`) is the ONE token grammar behind `/api/photos` (`Photo::search_photos`) and the unpaginated `Photo::list_all_filtered` serving `GET /api/photos/map` — never re-implement it; the map listing is the only listing without `LIMIT`/`OFFSET` (the grid endpoint caps at 100, so a filter change must not silently truncate the map). The 2026-09 file-only date/coordinate invariant: the DB stores NO capture date and NO coordinates — `photos.taken_at` and the stored `$.location.latitude`/`longitude` keys are dropped by a NEW migration (an applied migration is content-checksummed, so the cleanup ships as a new file, never an edit — entry 8) and `db::stored_metadata` is the single `photos.metadata` serializer, stripping the two coordinate keys on EVERY write. `MediaFactsIndex` (`src/media_facts.rs`; in-memory, keyed by file PATH, which survives the in-app content-hash re-key) is republished by EVERY scan, unchanged files included — `full_rescan_and_cleanup` reads `read_media_facts_with_metadata` per file (its unchanged fast path too) and sets `MediaFacts::from(&ProcessedPhoto)`, so an external file edit is picked up by the next scan, and disappears via `remove_many` when the row is deleted. Only a sort whose key is a real column may be ordered/paged by SQLite (`is_sql_sort` + `build_order_clause`); the default listing and `sort=date` load the whole set, `enrich` every row and then `sort_photos` — a Rust mirror of SQLite's ordering, unknown date (`None`) first in ASC / last in DESC with the `hash_sha256` tiebreak in the same direction — and the month filter is a Rust `%Y-%m` compare on the enriched `taken_at`, so neither ordering nor month matching may be re-implemented in SQL (`NULL`-first/last and the tiebreak are the pagination contract). EVERY photo response is enriched from the index on the way OUT only — grid/map/listings, albums, collages, housekeeping candidates, single-photo GET/toggle/rotate, the PATCH reply and video `?metadata`, all immediately before the reply, NEVER before a DB write, and the PATCH handler re-reads the file with `facts.reload(&photo.file_path)` before enriching its response — and the in-memory pass is inside SC-003's 1 s budget at scale (5,000 rows: `sort=date&order=desc` 320 ms, `year=…&month=…` filter 239 ms, `/api/photos/timeline` 26 ms). The bulk date-shift capability is removed end to end (no route, no `BatchResult.skipped`, no frontend action). `video_processor::fix_moov_atom` MUST keep `-map_metadata 0`: the scan's in-place `+faststart` rewrite replaces a moov-at-end file, and without that flag ffmpeg drops the container's global tags — the only remaining copy of a video's `creation_time` (pinned by `test_fix_moov_atom_preserves_creation_time`) — so the app would re-date every such video from its birth time on the next scan.
